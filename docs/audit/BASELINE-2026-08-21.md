### Detalhe das 17 falhas de backend

**`NexTraceOne.Integrations.Tests` — 13 falhas — BUG DE PRODUÇÃO**
Todas com `System.ArgumentException : Tenant-scoped connectors must have a TenantId`
originada em `IntegrationConnector.Create` (`IntegrationConnector.cs:124`).

Verificado: os 12 pontos de chamada de produção em `NexTraceOne.Ingestion.Api/Endpoints/`
também não passam `tenantId` nem `isGlobal`, logo lançam em runtime no auto-provisionamento
do conector. `tenantId` e `isGlobal` são parâmetros opcionais, por isso o compilador não
obrigou nenhum chamador a mudar quando a invariante foi introduzida.

- `IntegrationHubFeatureTests`: `GetConnector_ValidId_ShouldReturnConnector`, `GetFreshness_ShouldReturnFreshnessSummary`, `GetHealth_ShouldReturnValidHealthSummary`, `GetIntegrationFilterOptions_ShouldReturnDistinctConnectorTypesAndSupportedStates`, `ListConnectors_WithData_ShouldReturnItems`, `ListExecutions_WithData_ShouldReturnItems`, `ListSources_WithData_ShouldReturnItems`, `ReprocessExecution_ValidId_ShouldReturnQueued`, `RetryConnector_ValidId_ShouldReturnQueued`
- `RetryConnectorTests`: `RetryConnector_ValidConnectorId_ShouldCreateExecutionAndReturnQueued`
- `IngestionPayloadParserTests`: `IngestionExecution_DefaultProcessingStatus_IsMetadataRecorded`, `IngestionExecution_MarkAsFailed_SetsFailedStatus`, `IngestionExecution_MarkAsProcessed_SetsAllParsedFieldsAndStatus`

**`NexTraceOne.BuildingBlocks.Security.Tests` — 3 falhas**
`AesGcmEncryptorTests`: `Decrypt_WithInvalidBase64_Throws`, `Decrypt_WithPayloadTooShort_Throws`,
`Decrypt_WithTamperedCiphertext_Throws` — todas *"Expected a `<System.FormatException>` to be
thrown, but no exception was thrown"*.

A implementação declara explicitamente o comportamento oposto:

> `/// <remarks>Fail-open: se o valor não for um ciphertext válido, retorna o texto original.</remarks>`

Não é um teste a apanhar uma regressão acidental — é um contrato contraditório entre
implementação e testes. O caso `Decrypt_WithTamperedCiphertext_Throws` é o relevante para
segurança: adulteração de ciphertext é silenciosamente ignorada.

**`NexTraceOne.Governance.Tests` — 1 falha**
`TestNetworkConnectivityTests.Handle_WhenTargetIsAccessible_ShouldReturnSuccessWithStatusCode`
— *"Expected result.Value.Success to be True, but found False"*. O teste faz um pedido HTTP
real; falha em ambientes sem egresso direto. Dependente de ambiente.

## `Test Backend (E2E)` e `OpenAPI Artifact` — credenciais de BD desalinhadas

Ambos falham com `28P01: password authentication failed for user "nextraceone"`
(51 testes no E2E). São **duas** causas distintas, ambas de configuração do workflow —
não defeitos de produto.

`appsettings.json` do ApiHost define as 9 connection strings com um **placeholder**:

```
NexTraceOne, IdentityDatabase, ServiceCatalogDatabase, ChangeGovernanceDatabase,
IncidentResponseDatabase, GovernanceDatabase, AiHubDatabase, IntegrationsDatabase,
ConfigurationDatabase
    →  Username=nextraceone;Password=REPLACE_VIA_ENV
```

Configuração dos jobs em `.github/workflows/ci.yml`:

| Job | `POSTGRES_USER` / `PASSWORD` | `ConnectionStrings__*` definidas | Resultado |
|---|---|---|---|
| `test-backend-integration` | `nextraceone_test` / `test_password` | — | conecta; falha depois nas migrations (P0 #5) |
| `test-backend-e2e` | `postgres` / `postgres` | **nenhuma** | as 9 strings pedem `nextraceone` → 28P01 |
| `openapi-artifact` | `nextraceone` / `nextraceone` | apenas `ConnectionStrings__NexTraceOne` | as outras 8 mantêm `REPLACE_VIA_ENV` → 28P01 |

### Porque o fallback não salva o `openapi-artifact`

`BuildingBlocks.Infrastructure/Configuration/ConfigurationExtensions.cs:27` implementa
`GetRequiredConnectionString(name, fallbackName)`. Devolve o valor específico do módulo
**se este não for vazio**, e só recorre ao fallback (`NexTraceOne`) quando está ausente:

```csharp
var value = configuration.GetConnectionString(name);
if (!string.IsNullOrWhiteSpace(value))
{
    return value;          // ← "…Password=REPLACE_VIA_ENV" entra por aqui
}
if (!string.IsNullOrWhiteSpace(fallbackName)) { … }
```

`IncidentResponseDatabase` e as outras 7 **não estão ausentes** — estão presentes com o
placeholder. O `IsNullOrWhiteSpace` é falso, o fallback nunca dispara, e o DbContext
tenta autenticar-se com a password literal `REPLACE_VIA_ENV`.

**Um placeholder é pior que um valor ausente:** derrota exatamente o mecanismo de fallback
desenhado para o cobrir. É a mesma família dos gates partidos — uma salvaguarda que parece
existir e não actua.

Correções: no `test-backend-e2e`, alinhar utilizador/password com as connection strings ou
definir os `ConnectionStrings__*`; no `openapi-artifact`, definir as 9 e não apenas uma.

## `Test Backend (Unit)` — como o job realmente corre, e porque fica vermelho

> **Correção.** Este ficheiro afirmava que os 188 testes dos 5 projetos fora de
> `NexTraceOne.sln` **nunca correm em CI**. Errado — assumi que o CI usava
> `dotnet test NexTraceOne.sln`.

O passo `Run unit tests` em `.github/workflows/ci.yml:109` não usa a solução:

```bash
while IFS= read -r proj; do
  dotnet test "$proj" --filter "FullyQualifiedName!~IntegrationTests&FullyQualifiedName!~E2E" …
done < <(find tests -name '*.csproj' \
          ! -path '*NexTraceOne.IntegrationTests*' \
          ! -path '*NexTraceOne.E2E.Tests*' | sort)
```

`find tests` apanha **todos** os projetos de teste, incluindo os cinco ausentes da solução.
O log confirma-o — `BackgroundWorkers.Tests`, `Selenium.Tests` e `VisualStudio.Tests`
aparecem nas linhas `──► dotnet test …`.

**O que resta do achado:** os 5 projetos ficam de fora de `dotnet test NexTraceOne.sln`,
o comando documentado em CLAUDE.md Parte 6. Quem validar localmente por essa via não os
corre; o CI corre. É uma divergência entre validação local e CI, não invisibilidade — e
não é P0.

### Porque o job fica vermelho

`tests/tools/NexTraceOne.VisualStudio.Tests/NexTraceOne.VisualStudio.Tests.csproj` declara:

```xml
<TargetFramework>net48</TargetFramework>
```

Num runner Linux, reproduzido localmente com o mesmo comando do CI:

```
A total of 1 test files matched the specified pattern.
System.IO.FileNotFoundException: Could not find 'mono' host. Make sure that 'mono' is
installed on the machine and is available in PATH environment variable.
Test Run Aborted.
EXIT=1
```

O passo tolera um único modo de falha:

```bash
if echo "$out" | grep -q "No test matches the given testcase filter"; then
  echo "::warning::Nenhum teste correspondente em $proj — tratado como pass."
else
  failed=1
fi
```

`Test Run Aborted` por falta de Mono não corresponde a esse texto, logo `failed=1` e o job
fica vermelho **independentemente do resultado real dos testes**.

O repositório já tem um job dedicado e Windows-only para a extensão (`build-vsix`); o que
falta é excluir este projeto do laço no runner Linux — por caminho, como já se faz para
`IntegrationTests` e `E2E.Tests`.
